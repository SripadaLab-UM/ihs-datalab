# Lab knowledge base

Status: **draft** for v1. This is a proposal under discussion and has not been
implemented.

The knowledge base holds the lab's shared, durable knowledge about IHS data:
what tables and variables mean, device quirks, cleaning and QC rules, how
features are computed, cohort definitions, known pitfalls, and reviewed
example queries. Agents read it so they stay grounded, anyone in the lab can
edit it, and GitHub keeps the history.

It replaces the prototype's "Knowledge Spine": a LinkML registry, custom MCP
servers, and an approval UI totalling about 12k lines of code for about 157
entries. The spine's *content* carries over. Its *machinery* does not.

## Design in one paragraph

The knowledge base is a folder of Markdown pages with a little YAML front
matter, kept in its own GitHub repository. Codex reads it through its native
mechanisms, `AGENTS.md` and skills, with no custom retrieval server. Agents
propose changes by editing files. A person reviews the diff and saves it,
which is a git commit and push done by DataLab. A small check script keeps
pages consistent and free of participant data. The design follows current
practice: Karpathy's "LLM wiki" pattern with human review added, and
OpenAI's "docs as the system of record, `AGENTS.md` as the table of contents"
guidance for Codex.

## Repository layout (`ihs-knowledge`)

```
AGENTS.md            ~100 lines: what this is, the no-participant-data rule,
                     how to read, cite, and propose edits
index.md             one line per page, grouped by folder (regenerated by the check)
sources/             one page per data source: fitbit.md, garmin.md,
                     healthkit.md, oura.md, sensorkit.md, surveys.md, mood.md …
tables/              one page per Oracle table/view worth explaining,
                     e.g. IHS_2025.VFITBITDAILYDATA.md
features/            derived measures, e.g. steps_day.md: meaning, device
                     precedence, caveats, link to the code that computes it
qc/                  QC rules, e.g. midnight-spanning-sleep.md
cohorts/             one page per cohort year: study window, quarter dates,
                     devices in use, and what's different about that year
queries/             verified query library: a question, its SQL, who checked
                     it and when, and the expected result shape (never results)
decisions/           lab decisions with reasons, e.g. "Oura excluded from
                     steps_day in 2025"
papers/              short summaries of lab papers, with DOI
generated/schema/    Oracle catalog metadata (tables, columns, types, comments),
                     one folder per cohort schema (IHS_2017 … IHS_2026),
                     refreshed by DataLab. Metadata only, never values
generated/drift.md   cross-year differences: tables and columns added,
                     removed, or renamed between cohorts
.agents/skills/      how agents use and maintain the knowledge base (below)
tools/check.py       the consistency and safety check
.github/workflows/   runs the check on every push
```

## Page format

```markdown
---
id: steps_day
kind: feature            # source | table | feature | qc | cohort | query | decision | paper
status: validated        # draft | validated | deprecated
summary: Daily step count combined across Fitbit, Garmin, and Apple Watch.
evidence:                # where the claim comes from: code, paper, query, person
  - code: ihsDataR/R/feature_steps.R
  - legacy: AggregateDailyMetrics_2024.R, lines 120–188
related: [sources/fitbit, sources/garmin, qc/midnight-spanning-sleep]
cohorts: [2024, 2025]    # which years this page applies to
updated: 2026-09-26
---

# steps_day

Plain-language explanation, caveats, and worked examples …
```

The rules are deliberately few:

- **Status matters.** Agents treat `validated` pages as fact. They must say
  when they rely on a `draft` page.
- **Every page has evidence.** "The model said so" is never enough.
- **Say which years.** Tables, columns, and rules drift between cohorts, so
  pages state which cohorts they apply to, and note differences.
- **No participant-level data, ever.** That means no IDs, no per-person dates,
  and no pasted rows or tables of values. Schema metadata and aggregate
  shapes are fine.

## How agents use it

Codex loads a small amount of guidance automatically and reads the rest on
demand. It doesn't need a search server at this size.

- **`AGENTS.md`** (always loaded) tells the agent the knowledge base exists at
  `/kb`, what the rules are, and to start from `index.md`.
- **Skills** carry the procedures. Each is loaded only when relevant:
  - `kb-use`: find relevant pages via `index.md` and grep, prefer `validated`,
    and cite page ids in answers.
  - `kb-propose`: when the agent learns something durable (a quirk, a rule,
    a verified query), write or update a page in the proposed format and run
    the check.
  - `kb-maintain`: find contradictions, stale pages, broken links, and
    tables referenced but not in `generated/schema`. Used on demand.
- The **verified queries** in `queries/` are the most valuable pages for data
  work. Published experience from OpenAI, Snowflake, and Databricks data
  agents is consistent on this: reviewed example SQL plus clear table and
  join documentation beats long prose.

If the knowledge base outgrows grep plus `index.md` (roughly thousands of
pages), we can add a local search tool then. Not before.

## How edits happen

1. When a session starts, DataLab puts a fresh copy of the knowledge base in
   the agent's workspace. The copy is up to date with GitHub.
2. The agent edits pages there like any other files. This works in both
   session types.
3. After each turn, DataLab diffs the copy against the original. If anything
   changed, the user sees a card: "Knowledge edits proposed (2 pages)",
   with the diff.
4. The user can edit, discard, or **Save & share**. DataLab then:
   - runs the check, including the participant-data scan;
   - commits as that user;
   - pulls, pushes to `main`, and handles the rare conflict with a
     "someone else changed this page" screen.
5. People can also edit pages directly in DataLab's knowledge base view, with
   no agent involved, using the same save flow.
6. Any change can be reverted from the history view in DataLab or on GitHub.

Other sessions only see a change after it has been saved and pushed. That is
also what keeps data-session material from reaching research sessions
unreviewed (see [SAFETY.md](SAFETY.md)).

## The check (`tools/check.py`)

It runs in DataLab before every save and on GitHub after every push.

- Front matter is valid, and ids are unique and match file names.
- `related` and `evidence` links resolve.
- Tables and columns that pages mention exist in `generated/schema`. After a
  schema refresh, this is what flags pages affected by schema drift.
- Participant-data heuristics catch things that look like study IDs, dates
  next to IDs, long numeric lists, or pasted tables. A hit **blocks the
  save** until a person confirms it's a false positive.
- It regenerates `index.md`.

## Codex memories: off

Codex has a native "memories" feature that writes summaries of past sessions
into its home folder. It stays **disabled**, for two reasons:

- it would store summaries of data-session conversations on disk, outside
  our review, and
- if that storage were shared, those summaries could reach research sessions.

Shared, reviewed knowledge belongs in the knowledge base. Personal notes can
be a later feature if people want them.

## Moving over from the prototype spine

The spine's roughly 157 entries map onto the new folders:

| Spine type | New location |
|---|---|
| DataSource | `sources/` |
| RawSchema, RawVariable | `tables/` + `generated/schema/` |
| Construct, CanonicalFeature | `features/` (constructs become sections or a glossary page) |
| FeatureRecipe | the `features/` page, linking to the code |
| QCRule | `qc/` |

- A one-time conversion script generates the pages. A person reviews the
  result before the first commit.
- The Oracle metadata export becomes the first `generated/schema/`.
- Summaries of the lab papers seed `papers/`.

## Decided

- DataLab commits directly to `main` after the person reviews the edit in the
  app. There is no pull request per edit.
- The repo is `ihs-knowledge` in the `SripadaLab-UM` GitHub org, the same org
  as the app.
