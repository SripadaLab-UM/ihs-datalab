# Release parity check: the prototype against v1

27 September 2026, synthetic data only. DataLab `d432242` (branch
`w3-parity`), ihs-pipelines `e547dc2` (branch `default-workflows`), the
prototype at `eea768c` (a `--no-local` clone; its uncommitted changes touch
no routine or R code). The harness is `scripts/parity/`; its README says
how it works and what each verdict means.

## Verdict

**The outputs match, except in how dates and times are written.** Every
routine and `daily_metrics_2025` succeeds on both sides, with the same
columns, the same row counts, the same QC outcomes and the same delivered
files, and every value agrees once dates are read as instants. The
remaining differences are formatting, each with a known cause:

1. **v1 writes dates and times differently from the prototype, on
   purpose.** The prototype's broker wrote every Oracle DATE in ISO form
   with a `T` (`2025-05-03T00:00:00`); v1 now writes `2025-05-03 07:30:00`,
   and a column that is all midnights as `2025-05-03`. This is DataLab's CSV
   writer (fixed in this branch; see below), and it is why 5 of the 8
   routines differ byte for byte, in their date columns only.
2. **R 4.6 writes a midnight datetime as a plain date.** v1's image has
   R 4.6.1, the prototype's R 4.2.2. Since R 4.3, `write.csv` writes each
   POSIXct value on its own, so a value at exactly midnight loses its
   `00:00:00` and a column mixes two shapes (`garmin_daily_summary_2025`'s
   `end`: 5,847 of 6,170 rows; `sleep_2025`'s `bed`: 2 of 42,105). Same
   instants, different text. This belongs in the pipelines repo, not
   DataLab: format the column before writing
   (`format(x, "%Y-%m-%d %H:%M:%S")`), which writes the same in both R
   versions.

With the same extract (pass 2), 7 of the 8 routines and 20 of 21
`daily_metrics_2025` files are byte-identical; the other two differ only by
cause 2.

## Can the prototype run on synthetic data?

**Yes, unchanged.** Its settings take the database from the environment
(`LAB_AI_ORACLE_HOST`, `_PORT`, `_SERVICE`, `_USER`, and the password from
`LAB_AI_ORACLE_PASSWORD`), and its broker's live executor connects with
them. The harness points it at `127.0.0.1:1522/FREEPDB1` as `DATALAB_RO`,
runs its broker on 127.0.0.1:8812 with the prototype's own metadata catalog,
and drives `RoutineStore` (the 8 default routines, seeded from
`config/default_routines.json`) and `IhsDataRPackageExecutor`
(`daily_metrics_2025`) in process, each with its real R executor in the
no-network `lab-ai-routine-r:local` container. The only stand-in is the
Dropbox upload, replaced by a copy into a folder.

## Method

- **Pass 1, end to end.** Each side extracts from the synthetic database
  itself, with each workflow's default parameters, and runs its own steps.
- **Pass 2, same extract.** The prototype's broker is replaced by one that
  hands back v1's extract byte for byte, so the R steps, QC and delivery
  run on identical input.
- v1 is a private practice DataLab on port 8802, driven through
  `/api/workflows`, reading a `git archive` of ihs-pipelines at `e547dc2`.
- For each workflow the harness compares the extracts, every output, the QC
  outcome (passed, rows checked) and every delivered file (subfolder, name,
  bytes). The five per-metric workflows v1 adds are each compared with the
  file of the same name from the prototype's `daily_metrics_2025` run.
- Nothing in this report is a row or a cell: only names, counts, value
  shapes, and means and sums of numeric columns.

**What this doesn't cover.** The Dropbox API itself; parameter values other
than the defaults; real data (in particular a Garmin HRV extract whose
calendar dates are all at midnight, which the synthetic database doesn't
hold; see below); the prototype's agent-side broker queries, capped
exports and UI; and Run again and Replay.

## The leads checked

**Garmin HRV days shifted by the date's time part (the `.hrv_garmin_daily_date`
calendar-date+1 rule).** *Not a parity difference on the synthetic data.*
`daily_hrv_2025` is identical in both passes, before and after the CSV
change. The prototype's extracts were not plain dates: its broker wrote
`YYYY-MM-DDTHH:MM:SS`, so the rule fired on every row in the prototype too.
The synthetic `VGARMINHRVSUMMARY.CALENDARDATE` holds times, so it fires on
both sides either way.

**The date format** is decided by what the lab's R code expects, not by the
prototype's bytes:

- **A space, not `T`.** Base R's `as.POSIXct("2025-05-03T07:30:00")` returns
  midnight without a warning, in both R versions (checked in both images);
  the space form parses. ihsDataR happens to use lubridate, which reads
  both, which is why the outputs agree.
- **A column that is all midnights as plain dates.** That is how R writes
  such a column, how the legacy scripts saw it (through ROracle), and what
  ihsDataR's fixtures and its Garmin test expect: a plain calendar date
  gets no +1, a date with a time does. A column with any time of day keeps
  every value's time, midnight included, so the rule behaves as it did in
  the legacy R. **To confirm with Yu:** if production's Garmin HRV
  `CALENDARDATE` is always at midnight, v1 now assigns those days as the
  legacy script and the tests do, and the prototype assigned them a day
  later. The synthetic data can't show this case.
- **RAW as upper-case hex**, as `RAWTOHEX` writes it, so a key reads the
  same whether the SQL converts it or not. `b'…'` and `<16 bytes>` were
  both unusable.

The change is in `datalab/data/oracle.py` (`csv_value`, `_dates_only`),
with tests in `backend/tests/test_oracle_csv.py`. It is the writer behind
every query, so chat, the Playground and workflows all get it. The unit
suite (1,275), the synthetic-Oracle suite (`-m oracle`, 206, which covers
the Playground and agent query paths) and the eval graders' tests (118)
pass. The model evaluations weren't rerun.

**Delivery folders named "… export run_…".** The workflow's name went
through the export's identifier scrub as one word: `fitbit_daily_2025` mixes
letters and digits the way an ID does, so all of it was removed and the
folder fell back to "export". The runner now passes the name with
underscores as spaces (`fitbit daily 2025`), so a year stays a year and a
real identifier in a name is still removed (`runner.delivery_title`, with
tests in `test_workflow_runner.py`). All 14 workflows delivered to folders
named after them.

## For the pipelines repo

- Format POSIXct columns explicitly before `write.csv` (cause 2):
  `garmin_daily_summary_2025`'s `end` and `sleep_2025`'s `bed` differ now;
  `start` in both Garmin routines, `end` in `garmin_sleep_summary_2025` and
  `sleep_2025`'s `wake` are built the same way and would differ as soon as
  a value falls exactly on midnight. The prototype's image wrote these with
  times throughout.
